## 2. 模块职责

| 模块 | 职责 | 输入 | 输出 |
| --- | --- | --- | --- |
| Gateway | 渠道适配、鉴权、限流 | 渠道消息 | 统一消息协议 |
| Guard-In | 入站净化与风险分级 | 原始 query | 净化 query + risk_flags + 路由建议 |
| Planner | 判断是否需要检索/调工具，还是直接闲聊/拒答 | 净化 query + 记忆 | 计划（走 ReAct / 直接答 / 拒答） |
| ReAct Subgraph | 推理—行动—观察循环 | 计划 + 历史 | scratchpad + tool_results + retrieved_docs |
| Retriever | ChromaDB 混合检索 | 查询 + 过滤条件 | Top-K chunks（带溯源） |
| Tool Executor | 调用**技能与工具**，封装容错 | 能力名 + 参数 JSON | `SkillResult` / `ToolResult`（成功/降级/失败），二者信封同构 |
| Reflector | 自我校验：是否满足约束、是否有矛盾、是否需补充 | 全部中间结果 | 通过 / 需重试 / 需澄清 |
| Guard-Out | 出站合规 | 草稿答案 | 终稿 + 风险提示 + 引用 |
| Checkpointer | 会话持久化 | state | thread 快照 |
| Profile Store | 用户长期偏好 | user_id | 画像 JSON（可删除） |

## 3. 一次完整请求的时序

| 阶段 | 发生什么 | 耗时预算 |
| --- | --- | --- |
| T0 | Gateway 接收，绑定 thread_id | 20ms |
| T1 | Guard-In：规则过滤（本地，无模型）→ 通过则直接放行 | 30ms |
| T2 | （仅命中可疑时）护栏小模型二次判定 | +150ms |
| T3 | Planner 首轮推理，输出 Thought + 首个 Action | 400ms（首字） |
| T4 | 技能调用 / RAG 检索（**并行**发起互不依赖的 Action） | 300–800ms |
| T5 | ReAct 第 2…N 轮（多数场景 1–2 轮结束） | 400ms/轮 |
| T6 | Reflector 校验（小模型，快速规则为主） | 150ms |
| T7 | Guard-Out：合规改写 + 风险提示注入 + 引用补全 | 100ms |
| T8 | SSE 流式返回 | 增量 |

> 优化要点：T1 与 T3 之间不阻塞；Guard-In 采用"规则先行、模型兜底"，只有可疑请求才付出模型开销。

## 4. 为什么这样选型

| 决策 | 理由 |
| --- | --- |
| **LangGraph** 而非纯链式 | 需要循环（ReAct）、需要条件分支、需要持久化中断（工单人工确认）、需要可回放的状态轨迹 |
| **ReAct** 而非纯 Function Calling | ReAct 的显式 Thought 让工具选择可解释、可审计；失败后能把错误语义化交回模型重试或换工具 |
| **技能独立部署为 HTTP 服务** 而非进程内函数 | ① 独立伸缩（菜单查询 QPS 远高于工单）；② 独立灰度与回滚；③ 故障隔离；④ 契约即文档，便于第三方/其他智能体复用 |
| **ChromaDB** 而非托管向量库 | 校内私有化部署、数据不出校；轻量、本地持久化、metadata 过滤能力足够；运维成本低 |
| **护栏双闸门（入站 + 出站）** | 只在入站拦不够——模型可能自己"编出"风险内容；出站强制节点保证 100% 覆盖所有分支 |
| **技能容错集中在调用器** | 容错策略一处实现、所有技能复用；技能内部只管业务与自身健康 |

## 5. 关键设计约束

1. **出站护栏是唯一的出口。** 图中任何分支（含错误分支、兜底分支、拒答分支）都必须汇聚到 `guard_out` 后才能到 `responder`。
2. **技能/工具调用永不抛出未捕获异常。** 一律转为 `SkillResult` / `ToolResult{ok:false, code, message, fallback}` 交回 ReAct 循环，由模型决定是否重试、换能力或降级回答。
3. **无召回不臆造。** RAG 未召回相关内容时，走 `insufficient_knowledge` 分支，输出"这块我暂时没有可靠信息" + 人工渠道；未核验（缺 `verified_date`）或状态非 `published` 的内容同样按"暂未查到"处理。
4. **写操作必须中断确认。** `feedback-ticket` 类工具在图中使用 `interrupt_before`，生成工单预览后等待用户确认。
5. **事实来自工具/检索，措辞来自模型。** 价格、时间、余量、位置等硬事实必须由工具返回或知识库提供，模型只负责组织语言；出站护栏会校验数字是否与来源一致。
6. **实时量不入库。** 拥挤度、排队时长、饭卡余额、天气等实时数据只由工具提供，不写入 ChromaDB；反之，静态事实不以工具返回值长期替代知识库。
7. **可选特征非强依赖。** 技能调用工具作为特征（如 S1/T2 用 T4 天气）时，工具不可用只退化为基线并标注 `feature_missing`，不得整体失败。
