# 04 · 技能（Skill）封装规范 ★

> 本规范是项目中"独立封装技能"的统一契约。**所有技能必须遵守**，这是主智能体能够自动发现、自动调度、自动容错的前提。

---

## 1. 什么是本项目中的"技能"

一个技能 = **一个可独立部署、独立版本、独立伸缩的 HTTP 微服务**，它：

1. 有清晰的业务边界（一件事做好）；
2. 有 **OpenAPI 3.1 契约**与标准 JSON 入出参信封；
3. 挂到主智能体的 **Tool Registry**，由大模型在 ReAct 循环中**自主选择调用**（非硬编码路由）；
4. 自带**健康检查、限流、超时、重试、熔断、降级、兜底**；
5. 无状态（水平扩容友好），状态外置到 Redis/Postgres。

---

## 2. 技能五要素（缺一不可）

| 要素 | 要求 |
| --- | --- |
| ① 契约 | OpenAPI 3.1 文档 + JSON Schema 入参校验；`GET /health`、`GET /openapi.json`、`GET /metrics` |
| ② 语义描述 | 供 LLM 理解的 `description` + 参数说明 + **2~4 个 few-shot 示例**（决定工具选择准确率） |
| ③ 容错 | 超时、重试、熔断、三级降级、兜底话术、幂等（写操作） |
| ④ 可观测 | 结构化日志、trace 透传（`X-Trace-Id`）、Prometheus 指标、错误码分类 |
| ⑤ 测试 | 契约测试 + 故障注入测试（超时/500/空数据）+ 红队用例 |

## 4. 统一 JSON 信封

### 4.1 请求

```json
{
  "request_id": "req_01J9Z8X7K2M3N4P5Q6R7S8T9V0",
  "skill": "canteen-menu-query",
  "version": "1.2.0",
  "action": "query_dishes",
  "params": { "key": "value" },
  "context": {
    "user_id_hash": "u_9f2c1a...",
    "locale": "zh-CN",
    "trace_id": "tr_01J9Z8X7K2M3N4P5Q6R7S8T9V0",
    "deadline_ms": 800
  }
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `request_id` | ✅ | 调用方生成，ULID；用于幂等与追踪 |
| `skill` / `version` | ✅ | 技能名与期望版本；主版本不一致时返回 `40003` |
| `action` | ✅ | 技能内子动作；未知返回 `40002` |
| `params` | ✅ | 业务参数，由各技能 JSON Schema 约束 |
| `context.trace_id` | ✅ | 全链路透传，技能日志必须打印 |
| `context.deadline_ms` | ❌ | 调用方期望的超时上限；技能取 `min(自身配置, deadline)` |

### 4.2 响应（成功 / 降级 / 失败**同构**）

```json
{
  "request_id": "req_01J9Z8X7K2M3N4P5Q6R7S8T9V0",
  "code": 0,
  "message": "ok",
  "data": { "...": "业务数据" },
  "meta": {
    "latency_ms": 86,
    "skill_version": "1.2.0",
    "data_version": "menu_2026-09-08_v3",
    "source": "upstream_api | cache | snapshot | vector_recall",
    "degraded": false,
    "cache_hit": true,
    "warnings": []
  }
}
```

**关键约定：**
- HTTP 状态码语义与 `code` 解耦：网络/协议层错误才用 4xx/5xx；业务失败统一 **HTTP 200 + `code != 0`**，这样主智能体无需区分异常与结果，直接把 `code/message` 喂回 ReAct 循环即可。
- 只有"服务进程不可用"才返回 5xx（此时由调用方熔断处理）。
- `meta.degraded=true` 时，主智能体**必须**在最终回答中披露（出站护栏强制追加"以现场为准"）。
- `data` 在失败时可为 `null`，但 `message` **必须给出可行动的信息**（如"暂无该窗口数据，建议查询一食堂"）。

### 4.3 统一错误码

| code | 含义 | 主智能体建议动作 |
| --- | --- | --- |
| `0` | 成功 | 正常使用 |
| `40001` | 参数校验失败 | 修正参数重试 1 次 |
| `40002` | 未知 action | 改为合法 action |
| `40003` | 版本不兼容 | 联系运维，不重试 |
| `40101` | 鉴权失败 | 不重试，转人工 |
| `40301` | 越权（请求了无权限的数据） | 拒绝并说明 |
| `40404` | 无匹配数据 | 放宽条件重试 / 相似推荐 / 告知用户 |
| `42900` | 限流 | 退避后重试 1 次，仍失败则降级 |
| `50010` | 技能内部错误 | 换工具或降级 |
| `50410` | 上游超时 | 重试 1 次 → 降级到缓存 |
| `50420` | 上游不可用 | 直接降级，不重试 |
| `50300` | 熔断中（快速失败） | 直接降级，不重试 |

## 5. 容错要求（硬性）

| 机制 | 配置 | 说明 |
| --- | --- | --- |
| 超时 | 连接 300ms / 读取 800ms；`min(自身, deadline_ms)` | 超时绝不无限等待 |
| 重试 | 最多 2 次，指数退避 100ms→300ms + 抖动；**仅幂等动作** | 写操作（工单）不重试，改走幂等键查询 |
| 熔断 | 10s 窗口内错误率 > 50% 且请求数 ≥ 20 → 打开 30s → 半开放 5 个探测请求 | 快速失败返回 `50300` |
| 三级降级 | ① 实时上游 → ② Redis 缓存（TTL 60s）→ ③ 昨日同餐次快照 → ④ ChromaDB 向量召回 | 每一级都改 `meta.source` 并置 `degraded=true` |
| 兜底话术 | 四级全失败 → `code=50420` + `message` 给出**可直接念给用户的话术** | 主智能体直接采用，不再改写事实 |
| 幂等 | 写操作必带 `request_id` 做幂等键，重复提交返回首次结果 | 防重复工单 |
| 限流 | 单技能令牌桶，超出返回 `42900` + `Retry-After` | 保护上游 |
| 缓存 | 热点 key（今日菜单）TTL 60s + 空值缓存 10s（防穿透） | 降低上游压力 |
| 数据校验 | 上游返回必须通过 Pydantic 校验；脏数据隔离为"该条缺失"而非整体失败 | 部分可用优于全盘失败 |

### 容错的分工原则

- **技能内部**：管好自己的健康（超时、重试、限流、自身降级到缓存）。
- **调用方（主智能体 `invoker`）**：管跨技能的通用容错（熔断统计、兜底话术、结果规范化、trace）。
- 两者叠加，任何一层单点故障都不会让对话崩掉。

## 6. 注册与自动调度

### 6.1 注册流程

```
技能启动 → 暴露 /openapi.json
        → Registry 定时拉取（或启动时注册到 Registry 表）
        → 解析为 Tool Spec（name / description / JSON Schema / few-shot / SLA / tags）
        → 生成 LangChain StructuredTool
        → 注入 ReAct 子图的工具列表
        → 健康检查失败的工具自动摘除，恢复后自动挂回
```

### 6.2 工具描述（决定调度准确率的 80%）

要求每个技能提供：

```yaml
name: canteen_menu_query
description: >
  查询校园食堂的真实菜单数据：某天、某餐次、某食堂/窗口供应哪些菜，
  含价格、辣度、主要食材、过敏原标签、余量状态、营业时间。
  当用户问"今天/明天/中午/晚上吃什么、有什么菜、多少钱、还有没有、几点开门"时使用。
  不要用于：营养估算（用 nutrition_analyzer）、人流排队（用 crowd_forecast）。
when_to_use:
  - "今天一食堂中午有啥？"
  - "红烧肉还有吗？多少钱？"
  - "食堂几点关门？"
when_not_to_use:
  - "帮我算一下这顿多少卡" → nutrition_analyzer
  - "哪个窗口人少" → crowd_forecast
examples:
  - { query: "三楼还有没有红烧肉", params: { canteen: "第一食堂", floor: 3, keywords: ["红烧肉"], available_only: true } }
```

> 经验：写清 **when_not_to_use**（负例）比堆正例更能降低误调用。

### 6.3 自动调度决策链

```
模型看到 工具列表（含描述与示例）
  → Thought：判断需要实时/结构化数据 → 选择 skill_call
  → 选定工具名 + 生成符合 JSON Schema 的参数（可由 Planner 提供缺失槽位，或 ask_clarify 追问）
  → invoker 执行（带容错）
  → Observation 结构化回写
  → 模型继续推理或 finish
```

**禁止**在主图里写 `if "菜单" in query: call_menu()` 这类硬编码路由——那不叫自动调度。

## 7. SLA 与验收

| 项 | 要求 |
| --- | --- |
| 可用性 | ≥ 99.5% |
| P95 延迟 | ≤ 500ms（不含降级路径） |
| 契约测试 | 每个 action 至少 3 用例：正常 / 边界 / 异常 |
| 故障注入 | 必须覆盖：上游超时、上游 500、空数据、脏数据、限流 |
| 文档 | README + openapi.yaml 必须与实现同步；CI 校验契约与代码 Schema 一致 |
| 版本 | 语义化版本；不兼容变更必须升主版本并保留旧版 30 天 |
